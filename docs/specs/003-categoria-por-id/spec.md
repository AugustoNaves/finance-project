## Objetivo

Hoje lançamentos, orçamentos e regras de importação guardam o **nome** da categoria. Renomear uma categoria faz as métricas e o gasto do orçamento zerarem; excluir deixa lançamentos apontando para uma categoria que não existe. Quando esta spec terminar, tudo aponta para a categoria pelo **identificador** (`categoryId`, com chave estrangeira): renomear reflete em todas as telas sem perder nada, e excluir uma categoria em uso é recusado com uma explicação do que a usa.

## Requisitos

| ID | Requisito |
|---|---|
| R1 | **Migration — vínculo.** Uma migration cria `categoryId` em `transactions`, `budgets` e `category_rules` e preenche cada linha com o `id` da categoria do **mesmo usuário, mesmo nome e mesmo tipo**: o tipo do lançamento (`transactions.type`, obrigatório desde a 004) para lançamentos; `outcome` para orçamentos; `category_rules.type` para regras. Assim, um lançamento `outcome` em "Outros" vai para o "Outros" de gasto, e não para o de receita ou investimento. A comparação de nome é exata (como o app compara hoje). |
| R2 | **Migration — órfãos.** Quando não existe categoria com aquele (usuário, nome, tipo), a migration **cria** a categoria (nome e tipo do registro, `color` e `icon` nulos) e vincula a ela. Vale para lançamentos e orçamentos. Uma categoria criada assim é única por (usuário, nome, tipo), mesmo com muitos lançamentos órfãos de mesmo nome. Regras de importação cuja categoria não existe **depois** desse passo são apagadas: hoje elas já são ignoradas pela sugestão (`categorize.ts` só usa regra de categoria existente). |
| R3 | **Migration — integridade.** Depois do preenchimento, `categoryId` vira `NOT NULL` nas três tabelas, com FK para `categories(id)` `ON DELETE RESTRICT` e índice; as colunas de texto `category` são removidas; o único de orçamento passa a ser `(userId, categoryId, month)` (o antigo é a constraint `budgets_userId_category_month_key`). A migration roda numa transação: se sobrar qualquer `categoryId` nulo, ela falha inteira e nada muda. |
| R4 | **API de lançamentos.** `POST`/`PATCH /api/transactions` recebem `categoryId` (o campo de texto `category` deixa de ser aceito). A API confere que a categoria existe, é do usuário da sessão e tem tipo compatível com o `type` (K3: `income`→`income`, `outcome`→`outcome`, `investment`→`investment`); no `PATCH`, a compatibilidade é conferida com o tipo e a categoria **resultantes** (o que veio no corpo, ou o que já está salvo). Falhas respondem `400` com mensagem e não gravam nada. `GET`, `POST` e `PATCH` devolvem `categoryId` e `category` (nome atual da categoria). |
| R5 | **API de orçamentos.** `POST`/`PATCH /api/budgets` recebem `categoryId`; a categoria tem de ser do usuário e do tipo `outcome` (senão `400`). Orçamento repetido para a mesma categoria no mesmo mês continua `409`. As respostas trazem `categoryId` e `category` (nome atual); `GET` mantém a ordem por mês desc e nome da categoria. |
| R6 | **Importação e regras.** `POST /api/imports/preview` sugere `categoryId` (e devolve o nome em `category` para exibição); `categorize.ts` passa a trabalhar com ids (regra, histórico e palavra-chave resolvem para o `id` de uma categoria existente do tipo certo). `POST /api/imports` recebe `categoryId` em cada item e em cada regra "Lembrar", e valida posse e tipo de todos **antes** de gravar (qualquer um inválido → `400` com o índice do item, nada gravado). `GET /api/category-rules` devolve `categoryId` e `category` (nome atual). |
| R7 | **Renomear e mudar tipo.** `PATCH /api/categories/:id` que muda só nome, cor ou ícone continua `200`, e lançamentos, orçamentos e regras passam a aparecer com o nome novo em todas as telas, com as mesmas métricas e orçamentos. Mudar o **tipo** de uma categoria em uso responde `409 { error, usage }` (mesmo formato do R8), porque deixaria lançamentos com categoria de tipo incompatível; categoria sem uso pode mudar de tipo. |
| R8 | **Excluir em uso.** `DELETE /api/categories/:id` de categoria usada por algum lançamento, orçamento ou regra responde `409 { error, usage: { transactions, budgets, rules } }` (contagens do usuário) e não apaga nada. Categoria sem uso é apagada (`200`); id de outro usuário ou inexistente continua `404`. |
| R9 | **Tela de Categorias.** Ao confirmar a exclusão de categoria em uso, o diálogo mostra a mensagem da API dizendo quantos lançamentos, orçamentos e regras a usam e o que fazer (editar esses lançamentos/orçamentos ou excluir as regras, ou renomear a categoria); a categoria continua na lista. O texto de confirmação deixa de dizer que "os lançamentos continuam com esse nome". Depois de renomear, a lista de lançamentos em memória é recarregada (`refreshTransactions`), para que Mês e Lançamentos mostrem o nome novo sem recarregar a página. |
| R10 | **Formulários enviam `categoryId`.** A folha Registrar/Editar (`TransactionForm`, aberta por `EntrySheetContext`), o `BudgetForm` e a conferência da importação escolhem e enviam o `categoryId`; categorias homônimas de tipos diferentes ("Outros") enviam ids diferentes. Some o caminho de "categoria preservada" que existia para nomes órfãos. |
| R11 | **Somas por categoria usam o id.** Gasto do orçamento (Mês e Planejar), métricas de Categorias, "Gastos por categoria" e "Categoria líder" de Relatórios, distribuição de Investimentos, ordem de "mais usadas" no formulário e o filtro de categoria de Lançamentos agrupam e comparam por `categoryId`, exibindo o nome. |
| R12 | **Exportação.** O CSV de Configurações mantém as colunas atuais; a coluna `category` traz o nome **atual** da categoria. O JSON exporta os lançamentos como a API devolve (com `categoryId` e `category`). |

## Fora de escopo

- **Mover os lançamentos para outra categoria ao excluir** (ou "mesclar categorias"). É desejável, mas fica fora: (1) esta spec já carrega a migration mais arriscada do ciclo (três tabelas, órfãos, remoção de colunas) e precisa de escopo pequeno; (2) mover orçamentos exige uma regra de produto que ainda não existe (o destino já tem orçamento no mesmo mês: somar, manter o do destino, recusar?); (3) há caminho alternativo sem perda: renomear a categoria, ou editar os lançamentos. A mensagem do `409` orienta esse caminho. Vira candidata a spec própria.
- Casar nomes legados ignorando maiúsculas, acentos ou espaços na migration: a comparação é exata, como o app sempre fez; nomes diferentes viram categorias diferentes (R2) e podem ser renomeadas depois.
- Camada de compatibilidade que aceite o nome (`category`) no corpo das rotas: o front e a API mudam juntos no mesmo deploy (ver T8).
- Categoria do lançamento `card_payment` (nula) e o tipo `refund`: são das specs 005 e 006 (K2, K3).
- Ícones próprios por categoria (fora do ciclo, visão geral) e qualquer mudança nas 18 categorias padrão do cadastro.
- Paginação de `GET /api/transactions` (P13, fora do ciclo).
